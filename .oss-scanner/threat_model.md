# Threat model: opensverige/webbplats

## What this project does

This is the source of opensverige.se, the website of a Swedish non-profit
association (ideell förening). Most of it is static HTML generated by Python
scripts in `tools/` and served by Vercel. The one backend is the membership
signup: a Supabase Edge Function in `supabase/functions/medlem/` writing to the
Postgres tables in `supabase/schema.sql`.

The member table (`medlemmar`) is the association's electoral roll. It holds
names, email addresses, Discord handles and, for organisations, company name,
organisation number and representative. It is personal data under GDPR. Its
confidentiality and integrity are what matter most in this repository.

Code comments and docs are in Swedish. `supabase/README.md` explains every
design decision in the signup flow and is worth reading first.

## Where untrusted input enters

1. **`POST /functions/v1/medlem`** (signup form) and
   **`POST /functions/v1/medlem/bekrafta`** (email confirmation). Public on the
   internet, `verify_jwt` is off on purpose: the statutes and Swedish law
   require that anyone can join without an account. Assume an attacker with
   `curl` who controls every header and body field.
2. **Responses rendered in the browser** by `site/bli-medlem.html` and
   `site/bekrafta.html`, and the token in the `?t=` query string of
   `/bekrafta`.
3. **Blog posts** in `innehall/blogg/*.md`. Many are written by an LLM bot
   (Redaktionen) and arrive as pull requests. Treat their content as
   attacker-controlled: a prompt-injected model may write anything.
   `tools/migrera-blogg.py` renders them to HTML on opensverige.se.
4. **GitHub Actions** in `.github/workflows/`, triggered by pull requests from
   forks and from the bot.

## Security goals

- Nobody outside the function can read the member register or the pending
  signups (`anmalningar`). RLS is on with no policies; only the service role
  key, held by the function, reaches the tables.
- Nobody can learn whether a given email address is a member. The signup
  response is identical for new, pending and existing addresses. Look for
  differences in status, body, headers or timing.
- Nobody can become a member with an email address they do not control.
  Confirmation tokens are 256-bit random, stored only as a SHA-256 hash, valid
  for 24 hours and single use.
- Mail sent from our domain cannot carry attacker-chosen links or HTML. Names
  and other fields are validated and escaped before they reach an email.
- Rate limits (per salted IP hash) and the daily mail cap cannot be bypassed in
  a way that lets one client block real signups for everyone.
- The client IP is never stored in clear, only `sha256(ANMALAN_SALT + ip)`.
- Blog content cannot execute script on opensverige.se.

## How to exercise it

- `cd supabase/functions/medlem && deno test --allow-net=jsr.io hjalp_test.ts`
  tests the pure helpers in `hjalp.ts` (escaping, validation, tokens).
- `deno check index.ts` typechecks the function. Its jsr: imports are cached.
- `service postgresql start`, then `su postgres -c "psql -d medlem"` gives a
  database with `supabase/schema.sql` loaded, for testing the constraints and
  unique indexes. There is no PostgREST or Supabase stack offline, so to run
  `index.ts` end to end, stub `fetch` or the Supabase client.
- `python3 tools/migrera-blogg.py --kontroll` checks the blog posts.
  `python3 tools/verifiera.py` checks links, sitemap and JSON-LD.

## How we rate severity

- **Critical:** reading the member register or pending signups, leaking the
  service role key, or writing arbitrary rows to the database.
- **High:** confirming a membership for an address you do not control,
  bypassing token expiry or single use, enumerating members at scale, stored
  XSS on opensverige.se, or making our mail carry attacker-chosen links or HTML.
- **Medium:** blocking real signups for everyone (quota or rate limit
  exhaustion from one client), checking a single address with real effort, or
  XSS that needs the victim to click a crafted link.
- **Low:** missing hardening headers, verbose errors that leak no data, issues
  in the maintainer-only scripts below.

## Lower priority

- `tools/deploy.py`, `tools/rostlangd.py`, `tools/bygg-og.py` and the other
  build scripts run only on a maintainer's machine, on content from this
  repository. Report them only if a blog post or other PR content can abuse them.
- The static marketing pages have no user input. A missing CSP alone is Low.
- Supabase, Vercel, Cloudflare and Resend themselves are out of scope.

## Deliberate choices, not bugs

- The function is public and CORS is not a security boundary. The Origin check
  only stops other websites in a browser.
- The honeypot field `webbplats` returns 200 with `{"ok":true}`.
- Member numbers come from an identity column and may have gaps.
- Rate limiting and the mail quota fail open when the counting query errors,
  so a broken counter never blocks a signup. Report it only if an attacker can
  trigger that error on purpose.
- Rate limiting trusts `cf-connecting-ip`, which Cloudflare in front of
  Supabase sets. Report it if the `x-real-ip` / `x-forwarded-for` fallback is
  reachable in practice.

## Reports and patches

English is fine. Keep patches minimal and in the existing style: Swedish
identifiers, ASCII-only comments in the TypeScript, no new dependencies. Run
`deno test` and `deno check` on any patch to the function.
